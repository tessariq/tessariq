## Summary

Two run-ref resolution errors are uncovered: attaching to a run that has already reached a terminal state, and passing an unknown run ID to either `attach` or `promote`.

## Motivation

`attach` has e2e coverage for reconciling an exited orphan, which is a different path from refusing a cleanly finished run. Both cases are pure resolution logic with no container involved, so they are cheap and deterministic.

## Acceptance Criteria

- An e2e case attaches to a finished run and asserts it fails without attaching, prints the evidence path, and states the run is not live.
- An e2e case passes an unknown run ID to `attach` and asserts a clean unknown-run error.
- An e2e case passes an unknown run ID to `promote` and asserts the same, with no branch or commit created.

## Test Expectations

- Build tag `//go:build e2e`; new cases live alongside the existing suite in `cmd/tessariq/`.
- Use `containers.StartRunEnv` and the default `runTessariq` helper (which passes `--no-update-agent`); add a `Start*` helper to `internal/testutil/containers/` if a new collaborator is genuinely required.
- No host-tool guards and no local fake binaries or servers: the container supplies every runtime dependency.
- Runs on GitHub Actions `ubuntu-latest` in the existing `e2e` CI job with no secrets, no credentials, and no billed model calls.
