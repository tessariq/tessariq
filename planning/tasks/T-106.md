## Summary

`.github/workflows/images.yml` has no tag trigger and never sets `IMAGE_VERSION`, so it always publishes `ghcr.io/tessariq/<image>:v0.1.0` (the `Taskfile.yml` default). Meanwhile `internal/adapter/claudecode.DefaultImage()` and the OpenCode equivalent derive their tag from `internal/version.Version`, which GoReleaser stamps from the release tag. The two are coupled by coincidence at v0.1.0 and diverge at the next tag.

## Motivation

For v0.1.0 the coupling is correct by construction: tag `v0.1.0` stamps `Version=0.1.0`, `DefaultImage()` resolves to `:v0.1.0`, and that is exactly the tag `images.yml` already pushed. At v0.2.0 it breaks — the release would ship binaries whose default image points at a `:v0.2.0` that no workflow ever builds, so every new user's first `tessariq run` dies at `docker pull`. The failure is unreachable until a second tag exists, which is why it was deferred out of the v0.1.0 release rather than fixed on the release path.

## Acceptance Criteria

- `.github/workflows/images.yml` gains a `push: tags: ["v*"]` trigger and derives `IMAGE_VERSION` from `GITHUB_REF_NAME` instead of inheriting the Taskfile default.
- `runtime/claude-code/Dockerfile` and `runtime/opencode/Dockerfile` take the reference-runtime tag as a `--build-arg` instead of hardcoding `FROM ghcr.io/tessariq/reference-runtime:v0.1.0`; `Taskfile.yml images:build` passes it.
- Release ordering guarantees images for `<tag>` exist before `release.yml` publishes binaries whose `DefaultImage()` resolves to that tag.
- The digest summary step in `images.yml` covers all three published images (it currently loops only `claude-code` and `opencode` while `images:push` pushes `reference-runtime` too) and reads the tag from the shared variable rather than a hardcoded `v0.1.0`.
- GHCR package visibility for newly created packages is documented, or automated via `PATCH /orgs/tessariq/packages/container/<name>` with a `packages:write` token, so the manual "make it public" step is not rediscovered per release.
- `scripts/changelog-release-notes.sh` fails instead of falling back to printing the bare tag when the requested section is absent, so the non-empty release-notes guard in `release.yml` becomes a real gate rather than a no-op.
- `internal/container` surfaces an actionable hint when a default `ghcr.io/tessariq/*` image pull is denied, naming package visibility and `--image` rather than emitting a bare `denied: denied`.

## Test Expectations

- Unit coverage for the pull-denial error message, extending the existing `denied` / `manifest unknown` table cases in `internal/container/probe_test.go`.
- Unit coverage asserting `changelog-release-notes.sh` exits non-zero for a missing section (script-level test or a Go test invoking it).
- Workflow and Dockerfile changes verified by a tag-triggered dry run on a throwaway tag before the real v0.2.0 tag.

## Notes

- Blocked until `v0.2.0` becomes the active milestone.
- Do not fix this on the v0.1.0 release path: any edit to `runtime/**`, `Taskfile.yml`, or `images.yml` re-triggers the image workflow and rotates all three published digests, invalidating digests recorded during v0.1.0 manual testing.
- GHCR creates each *new package* private but preserves visibility across new tags of an existing package, so the manual visibility step is one-time per package name, not per release. New image names introduced later will need it again.
- Recorded during v0.1.0 release preparation; see `docs/release-readiness-v0.1.0.md` for the surrounding assessment.
