## Summary

Allowlist composition has no e2e coverage of what actually lands in `egress.compiled.yaml`: the built-in agent profile under `--egress auto`, the effect of `--egress-no-defaults`, and the rejection of `--egress open` combined with `--egress-allow`.

## Motivation

Precedence between CLI flags, user config, and the built-in profile is the part of egress most likely to regress silently, and a widened allowlist is a security failure that no other test would notice. `allowlist_source` exists to make provenance auditable; nothing asserts it end to end.

## Acceptance Criteria

- An e2e case under `--egress auto` with Claude Code asserts `egress.compiled.yaml` contains the built-in profile hosts and that `allowlist_source` records `built_in`.
- An e2e case with `--egress-no-defaults` and explicit `--egress-allow` entries asserts the compiled allowlist contains only those entries and nothing from the built-in profile.
- An e2e case with `--egress-no-defaults` and no entries asserts the agent cannot reach its own API, proving the flag took effect.
- An e2e case asserts `--egress open --egress-allow ...` is rejected at validation with guidance toward proxy mode.
- An e2e case asserts CLI entries override user config, and that `allowlist_source` records `cli`.

## Test Expectations

- Build tag `//go:build e2e`; new cases live alongside the existing suite in `cmd/tessariq/`.
- Use `containers.StartRunEnv` and the default `runTessariq` helper (which passes `--no-update-agent`); add a `Start*` helper to `internal/testutil/containers/` if a new collaborator is genuinely required.
- No host-tool guards and no local fake binaries or servers: the container supplies every runtime dependency.
- Runs on GitHub Actions `ubuntu-latest` in the existing `e2e` CI job with no secrets, no credentials, and no billed model calls.
